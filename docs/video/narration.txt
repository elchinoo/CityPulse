## 1 am_liam
I run a city. Sensors from many vendors send me readings, firmware versions and locations, all day long.

The usual answer is four databases. One for time series. One for documents. One for maps. And one for vectors.

This is CityPulse, a sample app, with its simulator. The identity provider, the gateway and the vault are reference scaffolding. Swap any of them.

What you are watching is EDB Postgres on the AgentPG platform. One database, doing all of it.

## 2 af_heart
First, where things are. Every sensor reports a latitude and a longitude. Here is one, with its position.

On this laptop there is no PostGIS. So the Map tab says it is not available.

This is the live fleet instead, captured. PostGIS draws the districts. Their outlines are derived from the sensor positions.

The colour is the health of the sensors inside. The brown district is below ninety percent.

And you can ask what is near a point, in metres. One within-distance function, on an indexed geography column.

## 3 am_eric
Now the question an operator asks. What is wrong in this district, and have we seen it before?

On my laptop, the Explain tab answers with one SQL statement. One round trip.

Relational: the sensors, counted by state. Time series: the last hour, from a five minute roll-up. JSON: which vendor or firmware stands out among the problem sensors. Nothing is wrong right now, so nothing stands out.

No PostGIS here, so the geo part says so. And this fresh database has no past episodes, so the vector part says that. The other models still answer.

Open Show the SQL. It really is one statement.

Here is the same card on the live fleet, captured. All five models, in the same statement.

Geo: the nearest healthy sensors, nine metres away, and the neighbouring districts. Vector: three similar past episodes, found by pgvector.

## 4 af_heart
Now, live data. The simulator is sending readings right now.

A new vendor can send anything. A position, and any JSON, in one batch.

It lands in a JSONB column, with a GIN index, next to the relational columns. A plain query groups the sensors by vendor.

Now press burst. A flood of readings, a slow database, and a district going dark.

The flood and the slow database fill the gateway's write slots. Readings queue up, and sensors start missing reports.

A sensor is stale after three missed reports. The status engine re-judges every sensor every ten seconds.

Operational means ninety-seven percent of the sensors are healthy. Below that, degraded. Below eighty-five percent, a partial outage. Below fifty, a major outage.

The stale tile climbs first. Nothing is smoothed, so the verdict follows the sensors.

Offline comes later, after twelve missed reports. Bursts only act on the built-in simulator and the gateway. Real sensors you connect are never altered.

Watch the verdict.

There it is. The verdict has slipped.

## 5 am_liam
CityPulse reports its own health to PagerLens every fifteen seconds, and raises an alert when the verdict gets worse.

No one copies anything by hand. A URL and a token are the only settings.

PagerLens opens an incident for the city. It is a separate sample app, on the same platform.

The alert says which city, and what the verdict is.

PagerLens investigates from there. That is another video.

## 6 af_heart
What does the database say about itself? On this laptop, the Insights tab says not available. Those are EDB extensions.

On the live fleet, CityPulse's database has three of them installed. Stat monitor, postgres tuner, and query advisor.

This is the Insights tab of PayBroker, another app on the same fleet. The stat monitor lists the slowest statements.

The tuner suggests settings. The query advisor suggests indexes.

For CityPulse itself, the advisor suggested an index on the sensor table. About one percent. A suggestion, not a promise.

## 7 am_eric
One more thing. I want an analyst, or an AI agent, to read the fleet, but never the secrets.

This database user can only read.

Count the sensors: it works. Group them by vendor: it works.

Ask for the API tokens: permission denied.

CityPulse holds no personal data, so there is nothing to mask column by column. It simply denies the tables that hold secrets. And its readiness check reports the masking status.

So, look how much easier this is.

Time series, JSON, geography and vectors, in one Postgres. One statement answers what is wrong, where, and whether we have seen it. No four databases to keep in sync.

Try it yourself. Clone the project, and run docker compose up. The guide is in the docs folder.
