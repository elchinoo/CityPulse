# Video script: CityPulse, "My data is time series, JSON, geo and vectors"

**Title:** "My data is time series, JSON, geo and vectors: look how much easier this is"

**Length:** about 5 minutes (narration about 770 words, 8 scenes, spoken by three neural voices that change with the topic; the length is set by the audio, see [video/README.md](video/README.md)). Re-recorded 2026-10-28 (the earlier six-minute cut is replaced).

**Audience:** customers and EDB colleagues who run, or plan to run, sensor and IoT data. No Postgres knowledge beyond "it is a database" is assumed. The ecosystem (PagerLens, the identity provider, the simulator) is explained only as far as the story needs.

**Story (problem first):** the video opens with the operator's problem in its first sentence ("I run a city. Sensors from many vendors send me readings, firmware versions and locations, all day long."), names the usual answer (four databases: time series, documents, maps, vectors, next to the relational one) and, within the first 30 seconds (second 18), says plainly that CityPulse is a sample app, that the identity provider, the gateway and the vault are reference scaffolding you can swap, and that what you watch is EDB Postgres on the AgentPG platform, one database doing all of it. The landing moment is **"look how much easier this is"**.

**What is shown on screen (not described):**

1. The map of districts with outlines derived from sensor positions, coloured by health, and "what is near this point, in metres" (captured from the live fleet; the query is shown as labelled source text).
2. One SQL statement across relational, time series, JSON, geo and vector data (the Explain tab): run locally for the three models a stock Postgres can answer, captured live for all five.
3. Live data: the built-in simulator reporting, a new vendor's batch with a position and any JSON, the JSONB query that groups sensors by vendor, the burst, the verdict falling, and the alert hand-off to a real (local) PagerLens that opens an incident.
4. Insights: the extensions EDB and AgentPG add (edb_stat_monitor, edb_pg_tuner, query_advisor), captured from the live fleet.
5. A read-only database user that reads the fleet and is denied the secret tables (real `psql` output, local database).

**Honest limits that the narration says out loud, and the ones it does not need to:**

- **PostGIS and the edb_* extensions do not exist on a stock local Postgres** (checked on this machine: `CREATE EXTENSION postgis` and `CREATE EXTENSION edb_stat_monitor` fail with "extension is not available"). So the Map, the geo and vector parts of the Explain card, and the Insights are real captures from the live AgentPG fleet of 28 Oct 2026, shown as stills with a slow zoom and highlight boxes under the banner *CAPTURED from the live AgentPG fleet, 28 Oct 2026*. Nothing in them is retyped or redrawn. The local Map and Insights tabs are shown saying "not available".
- The `ST_DWithin` query of scene 2 is **source text** (`src/citypulse/geo.py`, `nearby()`), labelled "SOURCE TEXT, not run in this video". The nine-metre figure in scene 3 is the captured Explain card, not a run of that query.
- Scene 3 locally: the card shows relational, time series and JSON; geo says PostGIS is missing and vector says this fresh database has no past episodes (the pattern memory fills every 15 minutes). The JSON part finds no vendor that stands out because nothing is wrong when it runs; the video says so.
- Scene 6: the Insights tab of **PayBroker** (same kit, same fleet) is shown for the stat monitor, the tuner and the advisor, labelled as PayBroker's tab. For CityPulse's own database only the extension list and the `ecoctl insights` advice (an index on `sensor.last_ts`, about one percent) are shown. The extension list capture of CityPulse's instance does not list `vector`, although the captured Explain card shows pgvector results: the list was captured at another moment; the video does not claim pgvector in that list.
- Scene 7: CityPulse holds no personal data, so there is no masked view in this app; the read-only role is denied the four secret tables (`app_setting`, `api_token`, `web_session`, `oidc_login`) by the kit's `deny_tables`. Shown on the local database; the readiness check's `masking` status is real output.
- CityPulse has no AI model, so there is no stand-in model in this video. **No high availability, failover or AIDB** is shown or claimed.
- Scene 5: PagerLens is a real, local PagerLens in the same throwaway cluster (its stand-in model is irrelevant: only the incident list and the incident header are shown). The video says PagerLens investigates "from there" and that this is another video.

**Voices (Kokoro, US accent, never in the middle of a scene; male and female alternate; opener am_liam; three voices; never af_nicole):** 1 am_liam, 2 af_heart, 3 am_eric, 4 af_heart, 5 am_liam, 6 af_heart, 7 am_eric, 8 af_heart.

## 1. Prerequisites and seed data (reproducible locally)

Nothing here needs a live service. Everything is fictional (the built-in simulator's sensors in "paris", a vendor called "Zephyr Metering").

- Machine: macOS, the CityPulse and PagerLens repositories side by side (each with `.venv`), Postgres 17 binaries with pgvector and `pg_trgm` on `PATH` (or `RECORD_PG_BIN`), `ffmpeg`, Node 22+, Google Chrome, and the Kokoro tool folder `videos/tts`.
- The recorder starts a **throwaway Postgres** (UTF8, 127.0.0.1 only, ports from `CITYPULSE_PORT_RANGE`), creates the AgentPG-like roles `a1p_readonly` and `cp_reader` before the migrations (so the app's hardening is applied), starts PagerLens and CityPulse (role `all`, 3,000 simulated sensors, city `paris`) with `PAGERLENS_URL` and an ingest token, signs in off camera, lets the fleet report for 5.5 minutes (charts need history), then films. A fresh database per take.
- Tokens never appear on screen: the terminal cards use shell variables, the browser never opens Settings, and the setup code and passwords are used off camera only.
